## Performance risks

1. **High — merchant full-table read.** `readAccounts` / `findAccount` / `findAccountByPhone` load every payload and filter in process. PK unused. Cheap at 205 rows; linear cost as merchants grow.
2. **Medium — events hard cap.** After 2000 rows, older events disappear from the product. Today 181 < 2000, so no user-visible loss yet.
3. **Medium — unfiltered guard sort.** Admin listing will degrade without a `created_at` index once the table grows.
4. **Info — events seq scan despite `track_events_at_idx`.** Planner choice at current cardinality. Do not add a second `at` index in P15.2 until EXPLAIN ANALYZE at larger scale shows a real sort cost.

---

## Concurrency risks

1. **High — merchant read-modify-write.** `upsertAccount` reads the full table, merges fields in memory, then upserts one JSONB row. Concurrent profile vs Guard freeze writes can clobber fields (`guardFrozen`, `resetCodeHash`, `plan`, …). No `SELECT … FOR UPDATE`.
2. **Medium — workspace last-write-wins.** `saveWorkspace` replaces the whole JSONB payload. Two overlapping saves for the same email can drop the earlier file list. No row lock.
3. **Info — `appendEvent` UUID + `ON CONFLICT DO NOTHING`.** Collision risk negligible. Historical SHA-256 ids stay. Do not unify.
4. **Low — `appendGuardDecision` has no `ON CONFLICT`.** A PK clash would make `queryPostgres` return null and the repository throw. Unlikely with UUIDs.

---

## Connection / pool risks

`getPool()`: `max: 5`, `idleTimeoutMillis: 10000`, `connectionTimeoutMillis: 1500`. No `statement_timeout`. No `idle_in_transaction_session_timeout`.

`queryPostgres`: swallows driver errors, sets `downUntil = now + 30s`, returns `null`. Catalog repos then `requirePostgres` and throw. A single timeout or connection blip poisons **all** catalog reads for 30 seconds. Isolated tests never point `DATABASE_URL` at live catalogs.

## Recommendations for P15.2 (do not start until explicit GO)

1. Change merchant reads to `WHERE email = $1` (and a dedicated phone lookup). Stop full-table RMW. Consider `SELECT payload FROM merchants WHERE email = $1 FOR UPDATE` inside a transaction for freeze/profile merges — **after** designing the merge, not as a blind lock.
2. Review orphans **before** any FK: keep or delete `p12.2-*` workspaces and `p125-*` guard rows. Adding `guard_decisions.email → merchants.email` now would fail on 52 rows.
3. Do **not** add UNIQUE/FK/CHECK until that orphan decision is explicit. Do **not** unify `track_events.id`.
4. Consider keyset pagination for `track_events` (`at`, `id`) before the 2000 cap is hit. Leave mixed SHA-256/UUID ids in place.
5. Consider `CREATE INDEX … ON guard_decisions (created_at DESC)` only if admin unfiltered listing stays in the product.
6. Do not add a second `track_events(at)` index until Seq Scan + Sort is actually expensive.
7. Narrow the 30s pool poison: log, fail the request, retry once; do not mark the whole process down. Add `statement_timeout`.
8. Workspace save: document single-tab last-write-wins, or add `updated_at` compare-and-swap — only if concurrent devices are in scope.
9. Leave `nac-demo.json` JSON-only. No catalog JSON restore.
