# P14.1 — Data-store contract lock

**Date:** 2026-08-25  
**Scope:** Freeze the current data-access boundaries with tests and this document. **No production write-path change.** Dual-write JSON + PostgreSQL stays as implemented after P12–P13.5.

This phase does **not** make PostgreSQL primary, does **not** add SQL migrations, and does **not** create a `database/` folder.

---

## Database access boundary

```text
Frontend / Shared / Financial Engine core / Guard policy
    ✗ PostgreSQL
    ✗ json-store
    ✗ repositories

HTTP handler (backend/src/http, Next BFF app/api)
    → validation, session, cookies, status codes
    → service
    ✗ server/db
    ✗ server/repositories
    ✗ pg / queryPostgres
    ✗ json-store

Service (server/services)
    → repositories (and domain helpers: parser, Guard run, mail)
    ✗ server/db
    ✗ json-store
    ✗ pg

Repository (server/repositories)
    → PostgreSQL adapter (server/db/postgres.ts)
    → JSON adapter (server/storage/json-store.ts)
    dual-write as implemented today
```

---

## Handler responsibility

`backend/src/http/*` maps HTTP only:

- Parse body / form, run Zod via `server/validators`
- Session: `requireMerchant` / `requireAdmin` / `optionalMerchant`
- CSRF via `backendApiRoute` → `assertSameOrigin`
- Call **one** service (or cookie-only helpers such as logout / admin me)
- Map `AppError` / Zod to `{ error }` + status

Handlers must not load or persist records.

Cookie-only handlers (`auth-logout`, `admin-me`) are allowed to use session/crypto without a repository. They still must not touch the database.

Next `app/api/*` stays a BFF: proxy or the same handler. It must not import the data layer.

---

## Service responsibility

`server/services/*` owns business rules (authn/authz decisions, analyze orchestration, Guard API façade). Data goes through `@/server/repositories/*` only.

Services must not call `queryPostgres`, `pg`, or `json-store`.

---

## Repository responsibility

These five modules are the **only** product layer that talks to durable stores:

| Repository | JSON | PostgreSQL | Dual-write |
| --- | --- | --- | --- |
| `user.repository.ts` | `users.json` | `merchants` | yes |
| `workspace.repository.ts` | `workspaces/{email}.json` | `workspaces` | yes |
| `event.repository.ts` | `events.json` | `track_events` | yes |
| `guard-log.repository.ts` | `guard-decisions.json` | `guard_decisions` | yes |
| `demo.repository.ts` | `nac-demo.json` | none | JSON only |

---

## JSON + PostgreSQL dual-write (locked, not changed)

**Read:** prefer PostgreSQL when rows exist; otherwise JSON. Some paths backfill JSON into PG when PG was empty.

**Write:** write JSON, then upsert PostgreSQL. On Vercel, if `DATABASE_URL` is set and the PG write fails, workspace/user paths **throw** (do not silently keep JSON-only).

P14.1 does not alter this order, the SQL, or the JSON paths.

---

## Fallback / backoff (locked, not changed)

`queryPostgres` in `server/db/postgres.ts`:

- Returns `null` if `DATABASE_URL` is empty (no pool).
- On query failure, sets a **30 second** `downUntil` window and returns `null` so callers fall back to JSON.
- `ensureGuardSchema` runs `CREATE TABLE IF NOT EXISTS` at runtime. That is **not** a migration system.

---

## Writes are not transactional

There is no SQL `BEGIN`/`COMMIT` wrapping JSON + PostgreSQL. A process can succeed on JSON and fail on PG (except the Vercel throw paths). **P14.1 records this; it does not fix it.** A Postgres-primary cutover is out of scope (future P14.3 at earliest, and only with an explicit product decision).

---

## What P14.1 is not

- Not a PostgreSQL migration
- Not `database/`
- Not changing Financial Engine, Guard, Auth, cookies, CSRF, CORS, NAC, or APIs
- Not deleting `lib/utils.ts` or landmine stubs
- Not removing leftover unused re-exports under `backend/src/storage/` and `backend/src/repositories/` (handlers do not import them; leaving them is not a write-path change)

---

## Enforcement

`tests/architecture-boundary.test.ts` → `describe("P14.1 data-store contract")`.

This behavior is **locked**. Changing the write path requires a later, approved phase — not a silent edit inside P14.1.
