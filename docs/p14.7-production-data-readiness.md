## 5. Track events — identity strategy (required before any event backfill)

This is the largest future problem. It is unchanged from P14.3/P14.4 and is now quantified.

```text
JSON TrackEvent  = { type, at, label?, email? }   // no id
PostgreSQL PK    = TEXT id, generated at insert by randomUUID()
appendEvent      = write JSON (still no id) then INSERT with a new UUID
mergeEvents      = JSON only; dedupes with at|type|label|email; unused by HTTP
```

If a backfill INSERTs the 97 JSON events with **new** UUIDs:

- there is no way to point a JSON row at its PG row
- a later dual-write `appendEvent` of the same payload creates a **second** UUID
- if PG already has some events from dual-write, JSON-only leftovers cannot be matched to them

**Do not backfill `track_events` until an identity strategy is approved.** Recommendation (not implemented):

| Option | Idea | Cost |
| --- | --- | --- |
| **A. Deterministic id (preferred to discuss)** | Derive PG `id` from the existing natural key `at\|type\|label\|email` (hash / UUIDv5). Use the same function in backfill **and** `appendEvent` | Requires a repository change (later slice). Current snapshot has 0 natural-key collisions |
| **B. Stamp JSON with UUID** | Generate ids once, write them into `events.json`, then INSERT those ids | Mutates JSON; changes the TrackEvent shape; still need `appendEvent` to persist id |
| **C. Defer events** | Backfill merchants / workspaces / guard first; leave events JSON-primary until A or B | Honest with P14.4 (events have no backfill today). Still NO-GO for a *full* cutover |
| **D. New UUID per JSON row, ignore matching** | Fast and wrong | Duplicates under dual-write. **Reject** |

Option D is not acceptable. A or B need an explicit later slice. C is only a partial plan, not a GO for PostgreSQL-primary.

## 9. GO / NO-GO criteria

**GO** for starting a planned JSON → PostgreSQL backfill requires **all** of:

1. `DATABASE_URL` set in the target environment.
2. PostgreSQL reachable with SELECT.
3. `schema_migrations` exists and `001_current_schema.sql` is recorded as applied.
4. Live `public` catalog matches 001 (or extras are explicitly accepted in a follow-up note).
5. Live counts captured for merchants, workspaces, track_events, guard_decisions.
6. JSON-only rows inventoried (including hosted Vercel `/tmp` if that environment is in scope).
7. Merchant emails normalized; PG PK equals `payload.email` on sampled rows.
8. Workspace `ownerEmail` matches `fileSafeEmail` and accepted merchant/orphan policy.
9. Track-event identity strategy **approved** (A or B above, or an equivalent that is not D). Event backfill does not start on randomUUID-only inserts.
10. Guard JSON ids do not collide with existing PG ids (or a documented merge rule exists).
11. Anomalies accepted in writing: 2 merchants without password; 2 workspaces without a merchant; 10 guard emails without a merchant.
12. Backfill is a later explicit slice — not this document, not `readAccounts`, not `db:migrate`.

**Any UNKNOWN on 2–6, or no approved event identity, is NO-GO.**
