### Why 002 was not created

The P15.3 GO required creating `002_*.sql` **only if EXPLAIN proved** `guard_decisions(created_at DESC)` useful. At **167** rows the planner uses Seq Scan + Limit at cost **35.26**. Merchant-scoped listing already uses `guard_decisions_email_created_idx`. An unused created_at-only index is not proven useful. Rollback of a never-applied migration is a no-op.

Revisit when `guard_decisions` is in the thousands (eval threshold: Seq Scan **and** ≥ 10_000 rows).

## Merchant concurrency

`upsertAccount` now:

1. `BEGIN`
2. `SELECT payload FROM merchants WHERE email = $1 FOR UPDATE`
3. Merge in process (same field rules as P15.2)
4. `INSERT … ON CONFLICT (email) DO UPDATE SET payload = EXCLUDED.payload`
5. `COMMIT`

Auth/API request and response shapes are unchanged. Merge rules are unchanged. What changed is isolation: two overlapping writes (for example Guard freeze vs lastActive) no longer read-modify-write without a row lock.

Least-risk choice vs compare-and-swap: **FOR UPDATE**. CAS on `updated_at` would reject the second writer with a new error shape (API change). FOR UPDATE serializes the merge on the existing PK and keeps last-write-wins only for the **insert** race of a brand-new email (same as today).

Failure shape: driver errors still become `Could not read accounts from the database` (no JSON fallback).

## Workspace concurrency — plan only

`saveWorkspace` is still last-write-wins JSONB upsert.

Compare-and-swap would need the client to send `expectedSavedAt` / `expectedUpdatedAt`, then `UPDATE … WHERE updated_at = $expected`, then **409** when `rowCount` is 0. That changes `POST /api/workspace`. P15.3 stops here.

Apply later only with an explicit GO if concurrent devices are in scope.
