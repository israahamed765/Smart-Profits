# P12.2 — CORS / Auth audit

**Date:** 2026-08-23  
**Cookie names/flags were not changed.** CORS was added on the **standalone backend process only**, not on Next.js.

## Current cookie behavior (unchanged)

| | Merchant | Admin |
| --- | --- | --- |
| Name | `sp_session` | `sp_admin` |
| httpOnly | true | true |
| sameSite | `lax` | `lax` |
| secure | production only | production only |
| path | `/` | `/` |
| domain | **unset (host-only)** | unset |

Browser never sees `SESSION_SECRET`. `NEXT_PUBLIC_API_BASE_URL` is a public origin string only.

## Designed cookie + origin split (do not “fix” with SameSite=None)

Host-only cookies are keyed by **host**, not port.

| UI | API | Cookie sent? |
| --- | --- | --- |
| `http://localhost:3000` | Next `/api/*` (same origin) | yes |
| `http://localhost:3000` | `http://localhost:4000` | **yes** (same host `localhost`) |
| `http://localhost:3000` | `http://127.0.0.1:4000` | **no** — different host. Not a bug to paper over. |
| Production Vercel UI | same Vercel `/api/*` | yes (current deploy) |

**Default `BACKEND_HOST` is `localhost`**, not `127.0.0.1`, so a direct browser call can work locally without changing cookie flags.

**Rejected in this phase:** setting `Domain`, flipping `SameSite` to `none`, or reflecting `Access-Control-Allow-Origin: *`. Those would be an Auth behavior change.

**Safer production path until Auth moves:** keep the browser on Next `/api/*`. Optionally set server-only `BACKEND_URL` so Next proxies Wave 1 routes to the backend process (BFF). Cookies never leave the UI origin.

## CORS (backend only)

Implementation: `backend/src/http/cors.ts` + `server/http/origins.ts`.

- Allowlist = exact values from `FRONTEND_ORIGIN` and `APP_URL` (comma-separated).
- Echo the request Origin only if it is on that list.
- `Access-Control-Allow-Credentials: true` only together with that echo.
- Unknown Origin: no CORS headers; preflight **403**.
- Never `*`.
- Next.js routes do not send CORS (same-origin UI).

Production must set explicit `FRONTEND_ORIGIN` / `APP_URL` (the live site origin). Empty allowlist ⇒ no cross-origin access.

---

## CSRF still required

`assertSameOrigin` runs inside `backendApiRoute` before the handler. Allowed hosts = request `Host` **plus** hosts of `FRONTEND_ORIGIN` / `APP_URL`.

CORS allow ≠ CSRF pass. An allowed Origin still needs a valid merchant cookie for `/api/workspace` and `/api/analyze`. `/api/nac*` remains CSRF-exempt and **not** on the backend process yet.

## Remaining risks (documented, not worked around)

1. Direct `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:4000` **will not** send `localhost` cookies. Use `http://localhost:4000` or the Next BFF.
2. Auth/Guard still `fetch("/api/...")` on Next. If the public API base points at the backend, login cookies are set by Next while workspace/analyze go to `:4000`. That is acceptable **only** with the same host (`localhost`).
3. Auth migration needs a Set-Cookie strategy (still NextResponse today). Do not start it until Wave 1 stays green.
4. `FRONTEND_ORIGIN` missing in production would block browser CORS to a split API; same-origin Next deploy is unaffected.

## Found during live verification (fixed)

Unauthenticated `GET /api/workspace` on `npm run backend` returned **500** instead of **401** (`AppError` name in logs, `instanceof AppError` false). CSRF-without-Origin on `POST /api/track` was also **500** instead of **403**. In-process contract tests still returned 401/403 because they share one module graph.

Cause: tsx ESM can load `server/errors.ts` twice, so `instanceof AppError` fails. Fix: `isAppError()` in `server/errors.ts` (name + numeric `status` + message). Status codes and messages are unchanged. This is not a cookie/CORS bypass.
